# QuantCheck analysis

## What QuantCheck is

QuantCheck is a **financial-data reliability benchmark and auditing toolkit**. It intentionally introduces realistic defects into clean financial datasets, tests whether an auditor can identify them, and measures how much those defects distort downstream research.

Its core workflow is:

```text id="ixnbz6"
Clean financial data
        ↓
Point-in-time snapshot
        ↓
Deterministic fault injection
        ↓
Sanitized audit input
        ↓
Detector findings
        ↓
Manifest-based scoring
        ↓
Research-damage analysis
        ↓
Human-readable audit report
```

The strongest part of the project is that it does not merely report “bad rows.” It connects data defects to false investment conclusions, such as altered company rankings, portfolio selections, returns, Sharpe ratios, and statistical confidence. fileciteturn0file0

## Why it is a strong project

QuantCheck combines several valuable areas in one coherent system:

- Quantitative research methodology
- Financial-statement and point-in-time data
- Data engineering
- Property-based and deterministic testing
- Statistical evaluation
- Command-line product development
- CI integration
- Research communication

The central idea is more defensible than a typical stock-prediction project. Instead of claiming that a strategy predicts markets, QuantCheck demonstrates whether the underlying data made the strategy appear better than it truly was.

## What the v2 harness improves

The v2 harness turns the original idea into a much more rigorous engineering specification. Important improvements include:

- Python 3.12 and a fixed toolchain
- Day-level financial dates
- The explicit rule `available_on <= as_of_date`
- Canonical Decimal serialization
- Deterministic IDs and SHA-256 hashes
- A sanitized `AuditInputSnapshot`
- Explicit record roles
- Row-order-independent target selection
- Exact fault-to-finding matching
- Defined false-positive denominators
- Separate logical case configuration and runtime metadata
- Detailed fault specifications and adversarial-review requirements

These details matter because QuantCheck itself is supposed to test reliability. A nondeterministic or ambiguous benchmark would undermine the entire project. fileciteturn0file1

# Recommended MVP boundary

The original concept proposes six defects:

1. Look-ahead leakage
2. Restatement overwrite
3. Unit drift
4. Duplicate observations
5. Missing observations
6. Entity swap

However, the v2 harness contains detailed specifications for four:

1. Look-ahead leakage
2. Unit drift
3. Duplicate observations
4. Revision overwrite

For a one-month, high-quality implementation, the **four harness-specified faults should be the MVP**. Missing-observation and entity-swap support should be post-MVP milestones unless development finishes early.

This avoids implementing six shallow detectors when four carefully tested detectors would produce a much more credible project.

## MVP product surfaces

The first public release should contain:

- Python API
- `quantcheck` CLI
- Reproducible benchmark runner
- Four injectors
- Four corresponding detectors
- Manifest-based scoring
- Downstream-damage analysis
- Streamlit forensic demonstration
- Automated tests and GitHub Actions
- Technical report and benchmark results

It should not initially contain:

- Machine learning
- Multiple financial-data vendors
- React or a custom web backend
- Real-time market data
- User accounts
- Cloud infrastructure
- Corporate-action processing
- A generic no-code rule engine

# Principal development risks

## 1. Detectors could cheat

The detector must not see the hidden fault manifest, original values, or reference-only records. Otherwise it is not detecting defects—it is reading the answer key.

The `AuditInputSnapshot` boundary should therefore be treated as a security boundary:

```text id="vw5qaj"
Injection system:
clean data + fault manifest + reference records

Auditor:
sanitized corrupted snapshot only
```

Tests must prove that hidden fields cannot cross this boundary.

## 2. Synthetic faults could be unrealistically easy

A detector that finds a value multiplied by exactly 1,000 is not impressive if every injected unit error uses that exact pattern.

Each fault needs:

- A documented real-world failure mechanism
- Multiple severity levels
- Subtle and obvious variants
- Negative controls
- False-positive tests
- A measurable downstream consequence

## 3. SEC data normalization can consume the project

SEC XBRL facts contain multiple concepts, units, forms, reporting periods, amendments, and overlapping observations. The SEC adapter should be deliberately narrow:

- Five to ten companies
- One or two revenue-related concepts
- Quarterly 10-Q facts
- A limited historical range
- Cached raw responses
- Preserved accession numbers

The project should not attempt to create a universal SEC fundamentals database during the MVP.

## 4. Revision overwrite is significantly harder

Revision overwrite requires distinguishing what was originally known from what was revised later. It should be developed after the first three fault types and may initially use controlled fixtures rather than pretending all SEC restatement behavior has been solved.

## 5. The damage demonstration could become a toy backtest

The downstream analysis must be simple enough to understand but meaningful enough to demonstrate damage. A cross-sectional revenue-growth ranking is better than a complicated trading system because the viewer can directly see which companies entered or left the ranking.

## 6. Presentation work may crowd out benchmark quality

The dashboard should consume existing benchmark artifacts. It should not contain separate detection or scoring logic. Otherwise the project risks having one implementation in Python and another hidden inside Streamlit.

### Milestone 2: Define canonical domain schemas

**Objective:** Create stable contracts for every artifact.

At minimum, define:

- `FinancialFact`
- `CaseConfig`
- `RuntimeMetadata`
- `FaultManifest`
- `FaultManifestEntry`
- `AuditInputSnapshot`
- `Finding`
- `AuditReport`
- `ScoreReport`
- `DamageReport`

Important fields include:

```text id="koitxe"
record_id
entity_id
concept
value
unit
period_start
period_end
filed_on
available_on
form
accession_number
source
as_of_date
```

**Required invariants**

- Dates are day-level values.
- Availability follows `available_on <= as_of_date`.
- Monetary values use Decimal-compatible canonical serialization.
- IDs do not depend on DataFrame row position.
- Logical case identity excludes runtime-specific values.
- Runtime metadata records code version separately.

**Exit criteria**

- Schema round-trips produce identical canonical JSON.
- Hashes remain identical across repeated runs.
- Reordering input rows does not change record IDs or case IDs.
- Invalid dates, values, and roles are rejected.

## Phase 2 — Core scientific vertical slice

### Milestone 5: Implement the point-in-time engine

**Objective:** Answer what information was available on a historical date.

Core operation:

```python id="4d578r"
snapshot = build_snapshot(
    facts,
    as_of_date=date(2025, 4, 30),
)
```

The engine should:

- Include only eligible information
- Handle same-day availability consistently
- Preserve provenance
- Select the correct historical version
- Avoid using later revisions
- Produce a canonical snapshot hash

**Exit criteria**

- Facts filed after the research date never appear.
- Same-day facts follow the documented rule.
- Later revisions cannot overwrite earlier knowledge.
- Repeated builds produce byte-identical canonical artifacts.

---

### Milestone 6: Complete the look-ahead vertical slice

**Objective:** Prove the complete QuantCheck concept with one fault.

Implement:

1. Clean point-in-time dataset
2. Look-ahead injector
3. Hidden manifest
4. Sanitized audit snapshot
5. Look-ahead detector
6. Exact matching
7. Scoring
8. Human-readable explanation
9. Downstream ranking comparison

**Example fault**

```text id="zx267n"
True availability: May 5
Corrupted availability: March 31
Research date: April 30
Leaked information: 5 days
```

**Exit criteria**

This complete workflow succeeds:

```python id="qhr53o"
clean = load_case(...)
corrupted, manifest = inject_lookahead(clean, seed=42)
audit_input = sanitize_for_audit(corrupted)
findings = audit(audit_input)
score = score_findings(findings, manifest)
damage = measure_damage(clean, corrupted)
```

The detector must explain:

- Which record is affected
- Why it violates point-in-time rules
- How many days leaked
- Which research decisions changed

This is the most important milestone in the project. No other fault should be implemented before it works end to end.

---

### Milestone 7: Implement the scoring engine

**Objective:** Ensure benchmark scores are scientifically defensible.

Support:

- True positives
- False positives
- False negatives
- Precision
- Recall
- F1 score
- False-positive rate
- Per-fault results
- Per-severity results
- Aggregate results
- Cases with zero positives
- Cases with zero findings

The matching rules must define exactly when a finding corresponds to an injected fault.

**Exit criteria**

- Exact matches score correctly.
- Near misses do not silently count as true positives.
- Duplicate findings do not inflate recall.
- False-positive denominators are explicitly tested.
- Aggregate metrics can be reconstructed from case-level artifacts.

## Phase 3 — Four-fault benchmark

### Milestone 8: Duplicate-observation fault

**Injector**

- Copies eligible observations
- Assigns deterministic created-record IDs
- Records source and created records in the manifest
- Supports severity through fault count or fraction

**Detector**

- Uses the defined business key
- Distinguishes exact duplicates from legitimate repeated facts
- Emits grouped evidence

**Exit criteria**

- Exact duplicates are found.
- Legitimate amendments or multiple units are not automatically mislabeled.
- Created records are scored against the correct manifest entry.
- Row order has no effect on injection or detection.

---

### Milestone 9: Unit-drift fault

**Injector variants**

- Unit label changed but value unchanged
- Value rescaled but unit unchanged
- Both value and unit changed inconsistently
- Subtle scale corruption
- Isolated versus repeated drift

**Detector signals**

- Concept-to-unit compatibility
- Historical unit consistency
- Scale discontinuity
- Cross-record comparison
- Evidence from neighboring periods

**Exit criteria**

- Obvious and subtle severity levels exist.
- Naturally volatile values do not automatically produce findings.
- Findings explain both the metadata inconsistency and value-scale evidence.
- Tests include currencies, shares, percentages, and non-monetary facts.

---

### Milestone 10: Revision-overwrite fault

**Injector**

- Selects a fact with at least two historical versions
- Replaces the earlier-known value with the later value
- Preserves the hidden original/reference relationship
- Records both versions in the manifest

**Detector**

- Identifies an unavailable revision appearing in an earlier snapshot
- Uses provenance and version history where permitted
- Explains which later filing contaminated which earlier research date

**Exit criteria**

- The original historical value is distinguishable from the later revision.
- The auditor cannot access hidden pre-corruption values.
- The detector catches overwrite cases without labeling every amendment as corruption.
- Controlled synthetic cases work before real SEC examples are added.

---

### Milestone 11: Complete the benchmark case framework

**Objective:** Run any supported fault through one standard protocol.

Each benchmark case should define:

```text id="ictuko"

```

**Exit criteria**

A single runner can execute:


and produce:

```text id="w0nkeb"

```

Re-running the same logical case should reproduce the same logical artifacts.

## Phase 4 — Demonstrating financial consequences

### Milestone 12: Build the downstream research experiment

**Objective:** Connect data quality to investment conclusions.

Recommended experiment:

> On each research date, rank companies by a simple revenue-growth signal using only information available on that date.

Compare:

- Clean ranking
- Corrupted ranking
- Repaired ranking
- Selected companies
- Rank movements
- Portfolio turnover
- Returns, only when defensible price data is available
- Sharpe ratio, only when enough observations exist

**Exit criteria**

- The same research code runs on clean, corrupted, and repaired inputs.
- The experiment never bypasses the point-in-time engine.
- At least one fault visibly changes a decision.
- Damage metrics are not hard-coded to a particular example.

---

### Milestone 13: Implement repair and replay

**Objective:** Show that correcting the fault restores the analysis.

The workflow becomes:

```text id="5tpk1e"
Clean analysis
Corrupted analysis
Audited findings
Applied repair
Repaired analysis
```

Repairs may initially be manifest-assisted for demonstration purposes, but this must be labeled clearly. The project should not claim fully automated remediation unless the detector can reconstruct the correct value independently.

**Exit criteria**

- Repairs create a new artifact rather than mutating the source.
- Every repaired record links to the finding that motivated the change.
- Clean and repaired results converge within a defined tolerance.
- Manifest-assisted and detector-only repairs are distinguished.

## Phase 6 — Evaluation and hardening

### Milestone 17: Build the experiment matrix

Run at least 100 deterministic cases across:

- Four fault types
- Three severity levels
- Multiple random seeds
- Clean negative-control cases
- Multiple companies or fixture families

A possible matrix is:

```text id="klzji4"
4 faults × 3 severities × 10 seeds = 120 corrupted cases
plus clean control cases
```

**Exit criteria**

- Every experiment has a unique logical case ID.
- Failed runs are recorded, not silently dropped.
- Aggregate results can be regenerated from individual cases.
- Seeds and configurations are published.

---

### Milestone 18: Conduct adversarial benchmark review

Test ways the system might look better than it is:

- Detector sees hidden fields
- Injection changes row order
- Duplicate findings inflate recall
- Exact fault count is inferred from configuration
- Severity labels leak fault type
- Detectors memorize fixture IDs
- Empty cases distort aggregate precision
- Same input produces inconsistent results
- Real but uncommon observations trigger false positives

**Exit criteria**

- A written threat model exists.
- Leak tests prove manifest isolation.
- Property-based tests cover determinism and invariants.
- Known detector weaknesses are documented honestly.

---

### Milestone 19: Performance and reliability hardening

Measure:

- Runtime by dataset size
- Peak memory usage
- Cache effectiveness
- Artifact size
- Detector scaling
- CLI startup time
- Benchmark reproducibility across environments

**Exit criteria**

- The selected demonstration dataset runs comfortably on a normal laptop.
- Benchmark execution does not require cloud infrastructure.
- Interrupted writes do not leave apparently valid partial artifacts.
- Large outputs are streamed or partitioned where necessary.

# Post-MVP milestones

## Milestone 23: Missing-observation faults

Add:

- Random missingness
- Company-dependent missingness
- Period-dependent missingness
- Survivorship-like filtering
- Reporting-frequency detector
- Missingness-distribution analysis

This is more difficult than deleting rows because the detector must know what observations should reasonably exist.

## Milestone 24: Entity-swap faults

Add:

- CIK/ticker mismatch
- Reused ticker simulation
- Company-name mismatch
- Partial metadata swap
- Scale-based anomaly evidence
- Identifier-history support

## Milestone 25: Additional data adapters

Potential adapters:

- ALFRED vintage macroeconomic data
- Customer-provided Parquet or CSV datasets
- Data-warehouse tables
- Vendor-feed snapshots

Every adapter should normalize into the same canonical fact schema.

## Milestone 26: Policy and rule configuration

Allow organizations to define:

- Accepted units by concept
- Publication-lag policies
- Required reporting frequency
- Severity thresholds
- Blocking versus warning rules
- Dataset-specific exceptions

## Milestone 27: Hosted team platform

Only after the local package proves useful:

- Stored audit history
- Team dashboards
- Dataset versioning
- Scheduled checks
- API
- Role-based access
- Incident review
- CI provider integrations
- Audit evidence export

## Milestone 28: Startup validation

Before building substantial cloud infrastructure:

- Interview 15–25 quant researchers, data engineers, and financial-data teams.
- Determine how they currently detect timestamp, revision, unit, and identifier defects.
- Learn whether the urgent problem is prevention, vendor evaluation, incident investigation, or compliance evidence.
- Run several design-partner datasets through a local prototype.
- Identify the first narrow paid workflow.

The likely initial commercial wedge is not “clean every financial dataset.” It is something narrower, such as:

> Reproducible point-in-time and revision testing for financial research pipelines before a dataset or strategy is approved.

# Recommended immediate milestone

Begin with **Milestone 0 and Milestone 1**, then implement the smallest complete case:

> Load a clean financial fact with a true filing date, create an April 30 point-in-time snapshot, move a May 5 availability date backward, audit the sanitized snapshot, match the finding to the hidden manifest, and show which company ranking changed.

Once that case is reproducible and fully tested, the rest of QuantCheck becomes an expansion of a proven architecture rather than a collection of disconnected features.
